# 代码质量约束

这个仓库的代码主要由 AI 编写，以后还要拿来学习 TypeScript、Node 和 React。所以规则尽量交给工具自动执行，不靠人记，代码也要让初学者读得懂。

## 什么时候检查

| 时机         | 范围       | 入口                                    |
| ------------ | ---------- | --------------------------------------- |
| 提交时       | 暂存的文件 | `.githooks/pre-commit` 运行 lint-staged |
| 本地完整检查 | 全仓       | `pnpm lint`，`pnpm check` 已包含        |
| CI           | 全仓       | `pnpm check`                            |

本地提交钩子检查暂存文件，CI 执行完整检查；远端是否阻止合并由实际分支保护配置决定。不能将本地钩子视为不可绕过的保障。Biome 的警告也按失败处理。

## 必须为零的规则

| 规则                | 要求                                                       | 为什么                                                   |
| ------------------- | ---------------------------------------------------------- | -------------------------------------------------------- |
| 禁止 `any`          | 不用 `any` 绕过类型                                        | `any` 会关掉类型检查，错误留到运行时才暴露               |
| 禁止 `!` 非空断言   | 不写 `user!.name`，先判断再用                              | 它只让编译器不再提醒，值为空时照样崩溃。测试文件除外     |
| 处理每个 Promise    | 异步调用要 `await`；确实不等结果就写 `void navigate(path)` | 没人接住的 Promise 失败时，错误会悄悄丢掉                |
| 不给参数重新赋值    | 派生值用新变量                                             | 同一个名字中途变含义，读代码时容易看错                   |
| 没有循环依赖        | A 引用 B，B 不能再引用回 A                                 | 循环依赖会带来加载顺序问题，也说明职责没分清             |
| 没有死文件          | 每个模块都要有人引用                                       | 没人用的代码只会误导读的人                               |
| React Hooks 规则    | 依赖数组写全，Hook 只在顶层调用，组件不定义在组件里        | 这是 React 行为出错的常见来源                            |
| 禁止 `console.log`  | 业务代码只用 `console.error`、`warn`、`info`               | 调试输出不能留到线上，还可能带出敏感内容。脚本和测试除外 |
| 文件名用 kebab-case | `account-menu.tsx`                                         | 全仓统一                                                 |
| 测试不留 `.only`    | 提交前去掉                                                 | 否则其他测试会被悄悄跳过                                 |

TypeScript 使用 strict 模式，并开启 `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes` 等选项，见 `tsconfig.base.json`。

## 只减不增的规则

质量棘轮会把实际扫描结果和 `scripts/code-quality-baseline.json` 比对。历史违规已清理，基线当前为 `{}`。新增违规会直接导致检查失败，`pnpm quality:update` 只会收紧基线。

| 指标           | 基线字段                         | 新代码上限              | 为什么                                                        |
| -------------- | -------------------------------- | ----------------------- | ------------------------------------------------------------- |
| 文件长度       | `lines`                          | 代码 400 行，CSS 500 行 | 太长通常说明一个文件做了多件事                                |
| 函数长度       | `noExcessiveLinesPerFunction`    | 100 行，不算空行        | 一屏看不完的函数很难读懂                                      |
| 认知复杂度     | `noExcessiveCognitiveComplexity` | 15                      | 分支和嵌套越多，越难推理                                      |
| 嵌套三元       | `noNestedTernary`                | 0                       | `a ? b : c ? d : e` 改用 `if` 或查表                          |
| 类型断言       | `typeAssertions`                 | 0                       | `as` 是让编译器相信你，外部数据要用 Zod 校验。`as const` 不算 |
| 空代码块       | `noEmptyBlockStatements`         | 0                       | 空的 `catch` 会吞掉错误。确实要忽略时写注释说明原因           |
| CSS 优先级倒序 | `noDescendingSpecificity`        | 0                       | 后写的规则反而不生效，容易看错                                |
| `!important`   | `noImportantStyles`              | 0                       | 它会让后续样式无法覆盖                                        |

测试文件不受这些限制。`packages/db/src/schema.ts` 不受文件长度限制，表定义会随数据模型增长。

## 运行时边界

`check-boundaries.mjs` 扫描所有 app／package 的运行源码、管理脚本和依赖声明，阻止已退役平台的 SDK、网关及凭据适配重新进入项目。浏览器仍只能引用安全 contracts 和前端依赖，不能导入数据库、队列、存储、供应商或 Node 模块。规则中的历史名称只用于拒绝检查，不是兼容入口。导入检查通过 TypeScript 语法树识别静态导入、重导出、字符串动态导入及 require，避免注释误报；同时约束 contracts 的浏览器安全性和 packages 不依赖 apps，覆盖相对路径及工作区包名。动态拼接路径不在静态检查的保证范围内。

API features 的生产业务代码不能引用 app/index/cloudflare/cloudflare-app 入口；业务实现不能引用其他业务的 routes，路由注册器仍可组合路由。跨应用导入仅保留主站 cloudflare-app 到图片 cloudflare-runtime、Worker 集成脚本到 API app 两条既有装配边界。测试可以引用本应用入口，但不能任意跨应用。检查覆盖字面量路径，不做完整别名解析或传递依赖分析。

## 界面文字检查

界面提供简体中文与英文。`scripts/check-ui-text.mjs` 扫描 `apps/web/src` 的 TS、TSX 源码（测试除外）：

| 检查项     | 要求                                                                   |
| ---------- | ---------------------------------------------------------------------- |
| 中文字面量 | 字符串、模板字符串和 JSX 文字里的中文只能写在 `*-messages.ts` 文案目录 |
| 英文文案   | 文案目录 `defineMessages` 的 `en` 版本里不能出现中文                   |
| 提示词引用 | “@图片N”是与服务端共用的提示词写法，不算界面文字                       |

不随界面语言变化的固定中文（语言菜单里的语言自称、交给模型的局部修改说明、家纺裂变的提示词标记、完成回执的校验标记）列在脚本的 `allowedFiles` 里并写明原因；新增条目要说明它为什么不是界面文字。注释不受这项检查影响。

## 中文注释检查

`scripts/check-code-comments.mjs` 只检查规则起点之后新增或改过的 TS、TSX、MJS 代码。旧代码没改到不会报错，所以不用批量翻译，基线也不用记录旧注释。

| 检查项   | 要求                                       | 范围                       |
| -------- | ------------------------------------------ | -------------------------- |
| 注释语言 | 含英文字母的注释必须同时有中文             | 改过的顶层声明里的全部注释 |
| 注释长度 | 一段注释最多 3 行                          | 改过的顶层声明里的全部注释 |
| 用途注释 | 导出的函数、类和箭头函数正上方要有中文注释 | 改过的导出声明             |

测试文件只检查改到的注释行，不要求用途注释。`biome-ignore` 和 `@ts-` 开头的工具指令不检查。

检查要用 git 历史比较代码，所以 CI 的 Quality 任务设置了 `fetch-depth: 0`。找不到起点提交时检查直接失败，不会悄悄跳过。不要修改 `ruleStartCommit` 来绕过检查。

## 报错时怎么处理

| 提示               | 处理                                                                     |
| ------------------ | ------------------------------------------------------------------------ |
| `不能新增违规`     | 改代码，不要改基线                                                       |
| `已改善`           | 运行 `pnpm quality:update`，把收紧后的基线一起提交。这个命令只会降低数字 |
| `没有任何文件引用` | 删除文件，或把它接入使用的地方                                           |
| `注释要写中文`     | 把注释改成中文，英文标识符可以保留                                       |
| `缺少中文用途注释` | 在导出声明正上方加一行 `/** ... */`                                      |
| `注释最多 3 行`    | 精简注释，说不完的内容写进 `docs/`                                       |
| `找不到规则起点`   | 拉取完整 git 历史，不要改 `ruleStartCommit`                              |

确实需要例外时，必须先得到项目负责人同意，再手动修改基线或加抑制注释。这些改动会出现在 diff 里。

文件或函数超限时按职责拆分，不要按行数硬切。

## 工具查不了的约定

- 名字要说清是什么：写 `selectedAssetIds`，不写 `data`、`tmp`、`arr`。布尔值用 `is`、`has`、`can` 开头。
- 先处理异常情况并提前返回，减少嵌套。
- 一个函数只做一件事，函数名能说清它做什么。
- 注释写用途和原因，不复述代码。工具只查语言、长度和位置，内容要自己把关，见[中文注释规范](node-ts-best-practices.md#中文注释)。
- 优先用直白的写法，不为少写几行用技巧。
- 外部输入都当作 `unknown`，用 Zod 校验后再用。
- 服务端数据用 TanStack Query，交互状态用 Zustand，能算出来的值不存 state。

## 文档检查

`pnpm docs:check` 已纳入 lint 与 CI 的 `pnpm check`。检查 Git 管理及本地未忽略的新 Markdown 文件，排除第三方技能快照；覆盖内联链接、图片、引用式链接定义、本地文件与井号标题锚点（含重复标题及中文）。跳过围栏和行内代码中的示例，不联网检查外部地址。

这是仓库常用 Markdown 语法的静态检查，不是完整渲染器：HTML href、Setext 标题、复杂嵌套括号链接和未定义的快捷引用需要人工复核。业务描述、版本、权限和部署状态仍要核对代码，链接通过不能证明文档事实正确。错误输出只包含文档路径、链接及错误码。
