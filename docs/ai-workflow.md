# AI 任务阅读与交接

本文只管理阅读、任务拆分和交接方式，不复制产品、视觉、接口或部署规范。根 [AGENTS.md](../AGENTS.md) 保留全局底线，目录规则补充本地要求。少读无关内容不等于可以忽略适用规则。

## 开始一个任务

1. 用一句话确定目标、可观察的验收结果及范围。不同目标另开对话；不要把服务器、客服等无关聊天传给代码执行者。
2. 用 `pnpm ai:context` 获取分支、HEAD、最近提交和最多 30 行文件状态；需要完整状态时执行 `git status --short --branch`。命令只读 Git 元数据，不读取文件内容、不联网，远端比较以本地跟踪引用为准。开发前按根规则 fetch/prune，能够快进时同步 dev，保留本地提交和修改。
3. 阅读根规则及涉及目录的 AGENTS。不能假定所有 AI 工具都会自动加载子目录规则；跨目录前主动读取。
4. 按任务索引选择文档，再用 `rg --files <目录>`、`rg -n '<符号或主题>' <目录>` 定位实现、调用方和测试。不要默认输出整棵目录、全部源码或全部技能。
5. 先核实当前代码。需求书中的“现状”带有时间边界，文档、聊天和交接摘要都不能替代代码与测试证据。

换到其他 AI 工具时，可以直接发送下面的启动指令，再附具体任务或交接记录。不依赖工具是否自动识别 AGENTS，也不需要复制原聊天：

```text
请在当前仓库完成以下任务：<目标与验收>。
先读取根 AGENTS.md，按 docs/ai-workflow.md 的任务索引选择文档和技能，
并主动读取所有涉及目录的 AGENTS.md。核对当前分支、提交及未提交修改。
任务依据/交接记录：<路径或简短正文；没有则说明>。
先验证记录与代码是否一致，再实施；追查相关调用方和失败路径。
完成适用检查并按仓库规则本地提交，报告实际检查、未验证项和提交 SHA。
外部操作授权：<仅填写用户实际授权；没有则停止在本地提交>。
```

## 按任务读取

以下是起点，不是允许修改的文件白名单。发现共享契约、权限、账务或跨运行时调用时，扩大读取范围，并遵守所有相关目录规则。

- **前端页面、布局、文案**：[Web 规则](../apps/web/AGENTS.md)；`apps/web/src/features/<业务>`。阅读：PRD 对应功能；DESIGN 通用与具名章节；使用控件时读 [组件清单](heroui-components.md) 和 [UI 一致性](ui-consistency.md)。
- **登录、账户、鉴权**：Web/API/DB 中实际涉及的规则；`features/auth`、`db/src/auth`。阅读：[企业鉴权](enterprise-auth.md)、[返回规范](api-response.md)；改登录 UI 时读 DESIGN「登录」；[账号设置任务书](account-settings-tasks.md) 是待开发需求。
- **任务提交、计费、重试**：[API](../apps/api/AGENTS.md)、[Worker](../apps/worker/AGENTS.md)、[共享包](../packages/AGENTS.md)、[DB](../packages/db/AGENTS.md)；各层 `images`、`wallet`。阅读：[生图 API](image-generation-api.md)、[企业钱包](enterprise-wallet.md)、[服务端分层](node-ts-best-practices.md)。
- **Webhook、无回调恢复**：API/Worker/共享包/DB 规则；`webhooks`、`images`、`queue`。阅读：[图片回调](image-webhooks.md)、生图 API 的相关生命周期、企业钱包的结算规则。
- **图片上传、转换、媒体访问**：API/Worker/共享包/DB 中涉及的规则；`packages/storage/src`、图片素材仓储。阅读：[对象存储](s3-storage.md)、[Cloudflare 部署](cloudflare-deployment.md)「图片处理」「绑定与 Secrets」、生图 API 上传部分。
- **主动推送、站内消息**：API/Worker/共享包/DB/Web 中涉及的规则；各层 `realtime`。阅读：[实时推送](realtime.md)；改提醒界面时读 DESIGN「右侧更新与消息」与「反馈、响应式与维护约束」。
- **数据表、SQL、迁移**：共享包/DB 规则及调用方。阅读：PostgreSQL 技能、服务端分层、[数据库命名](database-naming.md)、对应业务文档。
- **目录维护、公共代码重构**：被移动文件所在目录规则及导入方。阅读：[架构与目录](../PROJECT_STRUCTURE.md) 的相关目录和依赖方向、服务端分层；前端重构仍受 DESIGN 约束。
- **发布、绑定、域名、回滚**：根规则；涉及运行单元的目录规则及 Wrangler 配置。阅读：[发布流程](releasing.md)、Cloudflare 部署；授权范围不由文档授予。
- **文档维护**：根规则；修订的主题来源。阅读：[文档索引](README.md) 和对应规范；核对引用和当前实现，不重新加载所有源码。

### 产品与视觉的阅读边界

- 改产品行为先读 [PRD](../PRD.md) 第 1 节、标记含义及对应功能章节；新增入口、模型、计费或外部能力时，连同实现状态和规划边界核对。
- 改 UI 先读 [DESIGN](../DESIGN.md) 的定稿边界、第 1–3 节和第 10 节，再读涉及组件的章节。涉及浮层时同时读统一材质、关闭/焦点行为及会员页等具名例外。重构不能改变已定稿外观。
- 后端任务不影响 UI 时无需全文读取 DESIGN；若 API 变化改变界面状态、错误或交互，再补读相关章节。
- DESIGN 保持唯一视觉规范，不另建“AI 精简版设计”。章节可通过 `rg -n '^#{1,4} ' DESIGN.md` 定位，再读取相应范围；不要固定依赖可能漂移的行号。
- 技能按根规则和任务加载。先读适用的 SKILL.md，再读本任务需要的参考文件，不一次性加载 `.agents/skills`。忽略文件或目录不等于隐私授权，不能因此读取凭据和业务内容。

涉及计费、重试、存储中断或实时推送时，先用[业务测试索引](business-test-map.md)定位现有断言与待验证项，避免重复扫描全仓测试。

## 任务书和拆分

使用 [任务模板](templates/ai-task.md) 提供目标、依据提交、入口、范围、不变量和验收。单个小修复可直接在任务消息中填写，不必为每次改动创建文件。

- 一项任务尽量形成一个可运行、可验证的结果。跨前端、API、DB 的小功能不必机械拆给三个 AI；鉴权、提交和结算不能因分工失去完整责任人。
- 大需求先作为总需求保留，再按可独立验收的功能切分。账号设置任务书可按昵称、头像、企业成员、首次改密等目标拆分；共享会话契约和迁移需要先协调，不能假定这些任务完全独立。
- 明确哪些是用户已确认的决定、哪些是建议、哪些尚未验证。没有证据时写“待核实”，不能把计划标为已完成。
- 文件入口只帮助定位；执行者仍需追查调用方和失败路径。不要为了限制上下文而截断授权、计费、重试或兼容性分析。

## 接手与交付

使用 [交接模板](templates/ai-handoff.md)。在换 AI、换对话或较长任务中断时维护一份当前记录；不要把每轮聊天和完整终端输出逐条追加进去。长期业务决定更新原有业务文档。

交接时记录仓库/分支、依据提交、实现提交与未提交文件、已完成与未完成、实际检查及下一步。接手者重新核对这些信息；提交不同或存在新修改时先评估差异，不盲目重放命令。

- 不要求工作区总是干净，但必须区分本任务与他人的修改。摘要不能授权 reset、amend、覆盖文件、推送、部署或发送消息。
- 提交 SHA 是仓库状态依据，不能填写尚不存在的提交。部署成功还需独立记录目标、活动版本及实际线上验证；本地构建通过不等于已部署。
- 不传密钥、Cookie、用户提示词、素材、完整供应商响应、数据库导出或签名 URL。失败用错误码、经脱敏的必要堆栈和复现步骤说明。
- 输出以结论、改动路径和验证结果为主；长日志只读需要的片段，失败原因不明确时继续展开。不要反复读取已确认且未改变的同一内容。

## 浏览器验证的成本边界

纯按钮外观、间距、颜色和文案不跑 E2E，也不为此新增截图用例。登录、付费提交、草稿恢复、键盘焦点等关键行为变动，选受影响的 spec 或 --grep 定向验证一次；只有用户明确要求完整回归时才运行全量。不要把“改了 UI”直接解释成“所有浏览器测试都要重跑”。

开发时不以 check:release 代替定向测试；该命令现在只做 pnpm check。测试长日志重定向到本次 /tmp 文件，向对话输出结果摘要；失败再读取相关错误片段，不反复输出整份报告。

## 多 AI 与检查分工

默认由一个执行者完成任务，不因本文件存在而启动其他 AI。用户明确要求并行后，先约定职责和文件归属；其他分支/worktree 也须有用户请求，不改变根目录的 dev 开发约定。

- 独立模块可分工实现；指定一个集成人负责契约、迁移顺序、锁文件、共享 tokens 和最终提交。重叠文件不并发修改。
- 审查者从需求、diff 和关键调用链开始，确认相关规则，不必重复扫描全仓。高风险路径必须看实现，不能只认可执行者摘要。
- 日常迭代跑相关测试，代码完成后执行根规则要求的 `pnpm check`；DB/Queue、平台行为和关键浏览器交互仍按 [测试说明](testing.md) 验证。相关检查通过且代码未变时复用其结果，并记录对应提交/工作区依据。
- 文档改动运行 `pnpm docs:check`、`git diff --check`，并核对业务事实与规则迁移完整性。没有运行的检查明确写“未运行”和原因，不减少质量门禁来节省 token。

## 维护原则

根规则负责所有任务都需知道的底线，目录规则负责本地约束，业务文档负责功能事实，任务书负责本次范围，交接记录负责当前进度。各处链接到唯一来源，避免同一事实维护多份副本。

不预设具体节省比例。比较相似任务的阅读文件、重复查找和工具输出，再判断是否有收益；无需为此新增线上服务、向量库、依赖或自动采集用户内容。
