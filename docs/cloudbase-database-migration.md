## 实际执行

源为现有 Supabase `lycobo` 项目，目标为上海 CloudBase `lycobo` 环境（`lycobo-d9gyvxkegc54a1257`）。两端 PostgreSQL 均为 17.11。源连接使用该项目控制台提供的官方 Session pooler；未修改根 `.env` 或应用连接配置。

使用只读可重复读事务导出 PostgreSQL snapshot；`pg_dump --snapshot` 与逐表校验共享同一 snapshot。备份准备完成时间为北京时间 **2026-10-31 22:02:10**。范围限定为 `public`、`drizzle`，不复制 Supabase 的系统 `auth`、`storage`、集群角色或角色密码，不覆盖 CloudBase 的系统 schema。

目标导入前确认两个业务 schema 没有现存表、序列或视图，CloudBase 用户迁移历史为空。先创建表、枚举、函数和序列并限制访问，再以 25 个原子 DO 批次恢复数据与序列，最后建立主外键、唯一约束、索引和钱包保护触发器。数据导入文件包含业务私密内容，只留在 Git 忽略目录；Git 中仅记录不含业务行的结构迁移。

## 数据访问限制

43 张表均启用 RLS，撤销 PUBLIC、anon、authenticated 对导入业务表、序列和函数的直接访问。以 anon 和 authenticated 分别模拟读取企业账号表，均实际返回 `SQLSTATE 42501`。没有建立浏览器直连业务表策略；后续应用接入仍须在服务器解析企业身份并执行归属校验。

相比源库，额外对 Drizzle 迁移表启用 RLS。业务 UUID、密码哈希、加密密文、对象 key、时间戳和迁移记录保持原值；未创建演示账号或余额，未调用模型。
